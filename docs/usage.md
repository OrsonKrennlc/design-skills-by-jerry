# 使用方法与提示词

## 开始前

首次使用时，推荐先按[安装教程](platforms.md)让 Agent 一次装好本仓库的全部技能，再在任务中指定要使用的技能。确认当前 Agent 能读取你提供的材料；需要实际读写 Figma 时，再按[连接教程](figma.md)配置工具。只交付正文时可以直接使用附件材料。第一次使用 Agent，可以先读[使用入门](agent_intro.md)。

## 给 AI 什么材料

| 材料 | 用途 |
| --- | --- |
| 本次需求 / PRD / 已确认规则 | 确定用户任务和业务行为 |
| 当前 Figma 节点链接 | 定位 Page、版本、画面和状态；在 Figma 中用 Copy link to selection |
| 一份当前项目的定稿样例 | 沿用术语、语言、粒度和说明板样式 |
| 任务范围 | 哪些页面可写，哪些只是学习来源 |
| 交付方式 | 正文、Figma 说明板、可编辑页面与关键状态评审 |

使用下面的范例时，请随任务附上 Markdown 格式（`.md`）的 PRD，将 `【PRD】` 替换为附件文件名，其他 `【…】` 替换为实际 Figma 链接、目标 ID 和 Section 名称。

没有 PRD 时提供现有需求即可；不要为了使用技能补造一份。只提供学习链接不代表允许修改那个文件。需要英文说明板时直接说明，中文聊天不会自动要求翻译 UI。

## 电视交互说明

本节使用 `tvos-interaction-spec`，需要写入画布时连接可写的 Figma 工具。

```text
使用 tvos-interaction-spec技能，在【Figma链接】中完成任务：
需求：为【目标ID】编写电视页面交互说明。阅读【PRD】文档和【Figma中目标页面所在Section名】中的图片，了解任务目标、页面状态和遥控器操作规则，参考我给出的【Figma中参考说明所在Section名】中的定稿说明，沿用其语言、结构和版式。然后在【Figma中新建空白目标Section名】中完成说明。
每个状态写齐 Screen Design、Entry Point、Interaction 与 Controls，Controls 按各张图的实际焦点写，覆盖遥控器六键和返回焦点。
本轮只编写交互说明，不修改原 UI；缺少的业务规则请集中列出，不自行补成既定规则。
```

只要一行一页大纲时：

```text
使用 tvos-interaction-spec，把我提供的电视首页规则整理为行级交互大纲。
每行概括状态序列、入口、上下映射、左右边界、OK 和 BACK。
此轮只交付可复制正文，不在 Figma 建板。
```

重点检查：获焦和选中是否区分；六键是否对应当前焦点；入口、取消、保存和返回焦点是否互相一致。画面核对不等于电视端实测。

## Web 原型页面设计

本节使用 `web-prototype-design`，需要连接可写的 Figma 工具。

```text
使用 web-prototype-design技能，在【Figma链接】中完成任务：
需求：设计【目标ID】原型图。阅读【PRD】文档和【Figma中WAP所在Section名】中的图片，了解任务目标，预估所需要的组件，尽量从我给出的【Figma中参考风格所在Section名】中提取你需要的组件，不要重复造车轮。然后在【Figma中新建空白目标Section名】中完成设计。
完成可编辑页面和关键状态，用状态画面表达操作前后关系。
```

本技能交付可编辑页面与关键状态，不制作 Prototype 连线或可点击交互 demo。评审重点是业务依赖、状态变化与页面表达。

## Web 交互说明

本节使用 `web-interaction-spec`。只用上传资料写正文时，可以暂不连接 Figma。

```text
使用 web-interaction-spec技能，在【Figma链接】中完成任务：
需求：为【目标ID】编写 Web / 后台交互说明。阅读【PRD】文档和【Figma中目标页面所在Section名】中的图片，了解任务目标、字段规则和页面状态，参考我给出的【Figma中参考说明所在Section名】中的定稿说明，学习其语言、文字层级和写法。然后在【Figma中新建空白目标Section名】中完成说明。
说明画板名为 Interaction，背景纯黑 #000000、宽 1200、高度与对应完整页面相同，顶部对齐并紧贴页面右侧，间距为 0。
结构沿用 Entry → Function & Interaction，按当前画面的区域和控件组织，说明字段依赖、校验、保存、取消及错误反馈。
本轮只编写交互说明，不修改原 UI，也不扩写 PRD 未提及的实现细节；只有会改变当前任务结果的缺失规则或冲突需要集中列出。
```

只读审查时：

```text
使用 web-interaction-spec，只读审查这些页面与已有说明是否一致。
指出具体的 PRD / UX 或 UX / UX 差异，以及受影响的状态。
不要将 PRD 未展开的内容列成开发问题清单，不修改画布。
```

重点检查：每个状态有直接入口；字段依赖与保存/取消相容；当前版本准确；精确文案有依据；已解决的标记已清理。

### 原型对抗性审查

需要在写说明前复查原型时，明确要求审查模式。建议在独立会话中提供目标 PRD、当前原型和本次约束，不附上一轮生成者的自评结论；同一会话也应从 PRD 独立建立验收依据。

```text
使用 web-interaction-spec，对当前原型做对抗性审查。
PRD：[目标版本附件或链接]
当前原型：[节点链接]
范围：[本次功能、页面和关键状态]
交付标准：可编辑页面与关键状态评审，不要求 Prototype 连线。
约束：只能使用指定的现成组件库，不新增主组件、不 Detach 实例。

先从 PRD 和已确认规则独立提取验收条件，再对照当前设计。
核对明确需求是否被表达，并尝试未满足前提、切换上游、校验后修正、
保存、取消和失败恢复等本功能相关路径，查找矛盾或无法完成的任务。
每个问题给出依据、画面/节点、触发步骤、预期与现状、影响和最小修正建议。
区分已证实问题、待验证/待确认项和设计建议，不凑问题数量。
PRD 未展开的细节不自动判缺陷；静态图不能证明的行为列为待验证。
先交付审查报告，不修改原型或说明板。
```

需要接着写说明时追加：

```text
审查报告后，为无冲突部分在指定位置整理 Interaction 说明。
有冲突的部分分别列出 PRD 预期与设计现状，保留问题编号，
不把问题写成已确认规则；本轮不修改 UI。
```

验收重点是需求符合性与流程问题的证据是否成立，也要看误报。能识别问题不代表已修改原型，静态状态核对也不代表运行产品验证。

## 可选组合

安装完成后，可以先用 `web-prototype-design` 完成页面并评审定稿，再用 `web-interaction-spec` 为同一版本补说明。也可以只调用其中一项，不影响其独立使用。

需要审查环节时，可先产出原型，再用 `web-interaction-spec` 独立审查并汇总问题；按评审结论修订后，为当前版本整理说明。审查、修原型、写说明分别按用户指定范围执行。

组合时把页面修改和说明修改的范围分别说清楚。说明任务不会自动授权修改原 UI；读取样例也不会授权更改样例。

## 怎样判断本次任务完成

- **写作：** 覆盖指定页面和关键状态，有依据的规则完整，建议与未决项可分辨。
- **Figma：** 实际写入指定位置，文本可编辑、没有裁切重叠，附实际产物链接。
- **原型：** 报告页面、关键状态和实际静态核对范围，区分设计表达与运行产品验证。
- **工具不可用：** 给出当前资料支持的草稿，明确哪些实时读取或写回没有完成。

若 AI 只给泛化建议，可以继续指定：按技能读取当前节点、对照样例，直接完成本次明确范围，并按实际交付层级报告结果。
