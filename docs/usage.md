# 使用方法与提示词

先按[安装教程](platforms.md)装好技能。需要读写 Figma 时，再按[连接教程](figma.md)连接工具，并确认 Agent 能打开你提供的文件。只写正文可以直接使用附件。第一次使用 Agent，可以先读[使用入门](agent_intro.md)。

<summary>单独使用技能的提示词示例</summary>

下面的示例可以单独使用。附上 Markdown 格式（`.md`）的 PRD，把 `【PRD】` 换成附件名，其余 `【…】` 换成实际链接、目标 ID 或 Section 名称。没有正式 PRD 时，可以提供现有需求。Figma 节点链接可通过 Copy link to selection 获取。

参考链接只供 Agent 阅读；要修改文件，请另行说明。需要英文说明时也请直接提出，中文对话不会自动要求翻译 UI。

## 电视交互说明

使用 `tvos-interaction-spec`。写入画布需要可写的 Figma 连接。

```text
使用 tvos-interaction-spec技能，在【Figma链接】中完成任务：
需求：为【目标ID】编写电视页面交互说明。阅读【PRD】文档和【Figma中目标页面所在Section名】中的图片，了解任务目标、页面状态和遥控器操作规则，参考我给出的【Figma中参考说明所在Section名】中的定稿说明，沿用其语言、结构和版式。然后在【Figma中新建空白目标Section名】中完成说明。
每个状态写齐 Screen Design、Entry Point、Interaction 与 Controls，Controls 按各张图的实际焦点写，覆盖遥控器六键和返回焦点。
本轮只编写交互说明，不修改原 UI；缺少的业务规则请集中列出，不自行补成既定规则。
```

只需要一行一页的大纲时：

```text
使用 tvos-interaction-spec，把我提供的电视首页规则整理为行级交互大纲。
每行概括状态序列、入口、上下映射、左右边界、OK 和 BACK。
此轮只交付可复制正文，不在 Figma 建板。
```

检查焦点和选中状态是否分清，遥控器六键及返回焦点是否符合当前画面。画面检查只能核对图上的规则，不能算电视端的操作测试。

## Web 原型设计

使用 `web-prototype-design`。先规划，确认后再通过可写的 Figma 连接制作页面。

```text
使用 web-prototype-design，先通读【完整 PRD】，结合【组件库链接】完成全局 UX 规划。
梳理全部模块、页面与关键状态、模块之间的入口和数据依赖，评估组件复用与缺口，给出画面清单、预计张数和分阶段制作顺序。
区分明确需求与设计建议。本轮只交付计划，不绘制或改动画布，等待我确认。
```

有需求原型时可附上链接。规划确认后再发送：

```text
使用 web-prototype-design，沿用已确认的全局规划与设计约定，在【目标位置】制作【本轮模块】的 UX。
重读相关 PRD，并核对跨模块依赖。尽量复用组件库，可微调当前设计的样式，主题色沿用组件库。
按任务流程分行，必要的点击、hover 状态独立出图并标 cursor，弹窗和抽屉的背景压暗。
每页右侧紧贴一块空白 Interaction，纯黑、宽 1200 px、与完整页面等高。Interaction 右侧到下一页留 200 px，行间距 200 px。
检查页面、状态及模块衔接，交付节点链接和必要待确认问题。
```

## Web 交互说明

使用 `web-interaction-spec`。如果只根据附件写正文，可以暂不连接 Figma。

```text
使用 web-interaction-spec技能，在【Figma链接】中完成任务：
需求：为【目标ID】编写 Web / 后台交互说明。阅读【PRD】文档和【Figma中目标页面所在Section名】中的图片，了解任务目标、字段规则和页面状态，参考我给出的【Figma中参考说明所在Section名】中的定稿说明，学习其语言、文字层级和写法。然后在【Figma中新建空白目标Section名】中完成说明。
说明画板名为 Interaction，背景纯黑 #000000、宽 1200、高度与对应完整页面相同，顶部对齐并紧贴页面右侧，间距为 0。
结构沿用 Entry → Function & Interaction，按当前画面的区域和控件组织，说明字段依赖、校验、保存、取消及错误反馈。
本轮只编写交互说明，不修改原 UI，也不扩写 PRD 未提及的实现细节；只有会改变当前任务结果的缺失规则或冲突需要集中列出。
```

只检查页面和说明是否一致时：

```text
使用 web-interaction-spec，只读审查这些页面与已有说明是否一致。
指出具体的 PRD / UX 或 UX / UX 差异，以及受影响的状态。
不要将 PRD 未展开的内容列成开发问题清单，不修改画布。
```

## 原型审查

建议另开对话，提供当前版本的 PRD、原型和本次要求，让 Agent 从原始材料重新检查。同一对话也可以审查，但不能拿上一轮自评作为通过依据。

```text
使用 web-interaction-spec，对当前原型做对抗性审查。
PRD：[目标版本附件或链接]
当前原型：[节点链接]
范围：[本次功能、页面和关键状态]
交付标准：可编辑页面与关键状态评审，不要求 Prototype 连线。
约束：优先复用指定组件库，主题色沿用库内颜色，不修改共享主组件。

先从 PRD 和已确认规则独立提取验收条件，再对照当前设计。
核对明确需求是否被表达，并尝试未满足前提、切换上游、校验后修正、
保存、取消和失败恢复等本功能相关路径，查找矛盾或无法完成的任务。
每个问题给出依据、画面/节点、触发步骤、预期与现状、影响和最小修正建议。
区分已证实问题、待验证/待确认项和设计建议，不凑问题数量。
PRD 未展开的细节不自动判缺陷；静态图不能证明的行为列为待验证。
先交付审查报告，不修改原型或说明板。
```

需要接着写说明时，追加：

```text
审查报告后，为无冲突部分在指定位置整理 Interaction 说明。
有冲突的部分分别列出 PRD 预期与设计现状，保留问题编号，
不把问题写成已确认规则；本轮不修改 UI。
```

评审时要核对问题是否有依据、是否存在误报。问题找出来以后，还需要按评审结论修改；静态画面中的状态关系也需要在运行产品中验证。
