# Web 交互设计文档

把 PRD、当前 UX 和用户定稿中的交互规则整理成可共同使用的文档。先理解用户任务和当前设计，再说明有依据的触发条件、操作结果及业务约束；不把文档任务扩展为补写全部产品规则或开发细则。

## 交付与范围

- 交付载体、目标页面、语言服从当次请求和已有会话约定。要求在 Figma 内写作时，在目标页面旁更新或新增 `Interaction` 说明板；只要求草稿或未指定载体时，先交付可复制正文。提供学习用链接本身不意味着要修改该文件。
- 默认写入说明板及其必要容器，保留原 UI、原型、共享组件和用户定稿。用户已确认要同步修改 UX 文案或状态时，可更新对应的本地实例；授权不扩展到共享主组件或其他界面。
- 沿用目标项目的术语与文档语言。中文对话不等于要把英文说明板翻译成中文。没有项目样例时，正文默认使用用户的任务语言。
- 普通交互说明使用可编辑的 Figma Design 图层。不要擅自转换为 Figma Spec、FigJam、代码或 PRD；用户指定这些载体时再使用相应能力。

## 先读依据，再写规则

1. 定位独立 PRD；从链接定位具体节点、所属 Page、模块和版本，阅读相邻说明、真实界面文字、相关状态和可用原型事件。几何邻近用于找候选，内容用于确认配对，不能只信图层名称。不要把 Figma 的 `Requirements` 自动等同于 PRD。工作区镜像或 `sources/` 为空时，先在用户提到的实际项目目录及已知关联路径中定向查找，再请求来源；不做无关目录的全盘枚举。
2. 首次写作阅读 [写作方法](references/writing-guide.md)。需要查方法示例时，阅读 [方法与例稿](references/source-examples.md)；进入 Figma 排版前阅读 [画布规范](references/canvas-guide.md)。只加载当前任务需要的参考。
3. 区分四种依据：用户明确确认的规则；当前画面/原文明确表达的规则；设计建议；尚未确定的问题。前三者不能混写成同一种产品事实。原型缺失不否定明确的原文，静态截图也不能证明后台行为。
4. 用户当前定稿优先。其余依据按目标版本和适用状态判断，不凭节点 ID 大小、位置、出现次数或文案更详细判断新旧。业务冲突无法消解时，保留确定部分，集中列出受影响的问题。
5. 从样例学习写法和组织方式，不继承样例里的业务数字。名称上限、分页默认值、上传限制、状态联动、权限和计时必须来自本次项目依据。

## 控制粒度与评审

- 沿用来源的粒度。PRD 只写“模糊匹配”时，就写模糊匹配；不主动补充大小写、空格归一化、包含匹配、纠错或防抖时长，也不把这些实现细节逐项交给用户定稿。
- “PRD 未提及”本身不是 UX / PRD 冲突。实际差异要能指出两份依据及受影响的文案、状态或业务结果；文案措辞不同而含义一致时，标明只是文案差异。
- 只就会改变用户任务或业务结果、且确实阻塞当前交付的缺项提问。用户要求“PRD 没提就不注明”时，删除这类补充说明、建议和待确认清单；已明确确认的规则仍然有效。
- 用户要求逐项核实时，一次核实一个必要问题。确认后同步相关说明；在已授权范围内更新对应 UX，并清除已解决的差异标记。用户明确说“列为待办”才保留该待办，不把暂缓事项当成已批准规则。
- 用户重置或修改源设计后，先按当前页面重新定位、读取文字并截图，再判断原问题是否仍存在。原问题已解决就移除旧标记，不凭缓存节点或旧截图继续追问。
- `Review Notes` 保留可行动的真实差异、用户要求的待办及必要定稿结论。不要堆积开发问题清单、逐轮对话或核查日志。具体辨别方法见 [写作方法](references/writing-guide.md)。

## 组织页面与状态

- 先列出本次任务的页面/状态及对应说明。概览板交代页面模块与全局规则；抽屉、弹窗、悬浮、禁用、校验和保存反馈等状态按行为差异拆板。不要为同构选项机械复制全部正文。
- 本技能的学习基线是两部分：`Entry` → `Function & Interaction`。同项目新增板默认沿用；其他项目已有明确模板时沿用其模板，并补齐入口与行为的语义。
- `Entry` 写进入当前状态的具体来源和操作；中间态应写直接触发操作，不能一律复用模块首页入口。必要时说明进入后的默认值、选中项或可用状态。
- `Function & Interaction` 按当前画面的区域或控件排列，使用实际名称作小标题。字段、主操作、取消/关闭、反馈和跨控件规则按需要展开；`Rules`、`Triggering rule` 是条件性小节，不是每页必加章节。
- 通用规则放概览，局部状态写变化及必要前提。读者应能通过清楚的页面/规则引用找到通用约定；不要使用“同上”“见下一张”这类依赖画布位置的指代。
- 不套用电视文档的六键 `Controls`。Web 的鼠标、键盘、焦点、浏览器导航和响应式规则按实际交互需要描述。

## 写成专业、可执行的说明

- 以“条件 → 操作对象/动作 → 系统反馈 → 结果状态”为检查框架；简单行为用一句话写清，不为凑结构扩写。
- 直接描述行为：`Click Edit to open the drawer.`、`Required, single choice.`、`On success, the drawer closes...`。精确区分页面跳转、抽屉、弹窗、tooltip、新标签页和新窗口。
- 字段检查必填性、单选/多选、选项来源/排序、默认值、长度/范围/精度、依赖、校验时机及反馈；只写有依据且与当前交互相关的规则。
- 操作检查触发条件、可用状态、数据影响和成功结果；保存与取消分别说明。显示/隐藏、可用/禁用、选中/获焦、删除/停用/归档不能混用。
- 列表检查搜索范围与触发方式、筛选生效方式、排序/冻结列、截断/悬浮、分页与跨页选择。没有依据时，不默认实时搜索、模糊匹配、翻页保留选择或重置到第一页。
- 分支和约束先写条件再写结果；精确文案加引号，变量用 `{Name}` 等可识别标记。叙述语言可润色，产品标签与精确 UI 文案不能默默改写。
- 避免“进行相关操作”“合理提示”“优化体验”“正常处理”等不可验收的表述，也不罗列没有行为的 UI 标签。完整覆盖当前任务，不扩写成通用组件百科。
- 真正缺失的业务规则不要猜。先完成确定内容；仅按上述评审边界保留必要问题。未请求的实现建议不进入交互正文，不用反复注明“未定义”填充文档。

## Figma 排版与核验

- 使用当前环境的 Figma 读取/写入能力；使用官方 MCP 的 `use_figma` 前加载官方 `figma-use`；使用 Figwright 时改用其实际提供的读取、写入和截图工具，不假定存在同名官方工具或技能。缺少官方必需技能时先补齐依赖，或使用已连接的 Figwright；不能假装已加载。按节点分批读取文本、样式和必要几何数据，避免整页深层输出；截图用于核对文图关系和最终排版。
- 优先在原说明板更新。新增时沿用同版本邻近样例的尺寸、颜色、字体和层级，将说明与状态画面成对放置。1140×1080 可作为无现成模板时的示例起点，内容多时加高或拆续板，不压缩正文字号。
- 保持文本可编辑、自然换行，避免裁切、重叠和大段硬换行。写入成功后检查结构和实际渲染；跨多个说明板要逐板检查，不能只看第一块。
- 按用户要求标红真实差异时，用简短文字写明依据与差异；不要将 PRD 的沉默一律标红。用户定稿或重置后，正文、局部标记与汇总板保持一致。详见 [画布规范](references/canvas-guide.md)。
- Figma 访问失败时尝试已授权的可用读取方式；确实不能读取时，如实列出未取得的依据，并用已有材料完成草稿。没有取得原文不能声称学过它；未写回不能声称完成写回。

## 交付前检查

- 页面、入口和状态能对应；字段及 UI 标签一致，说明没有复制到错误版本或错误状态。
- 主操作、取消、关闭和关键失败路径没有互相矛盾；跨字段依赖不会让用户进入无路可走的状态。
- 本任务已有依据的空态、无结果、加载、失败等状态已核对。权限、键盘/焦点及小屏规则仅在来源或任务要求涉及的范围内检查，不把检查维度变成必须补齐的需求。
- 文档中的数字、默认值、选项和产品文案有依据，建议与待确认项可区分；没有把来源中的错字、重复标题和过期入口变成模板规则。
- 每块说明内容完整、样式一致、文字可读；长板扩展后没有覆盖下一行或邻近设计。
- 最终说明交付位置，链接到实际产物/节点，并只列必要的未决项。文档核对不宣称运行中的 Web 产品已经测试。
