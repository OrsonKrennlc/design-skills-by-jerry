# 写作方法：从画面到交互约定

以下字段和文案只作方法示例，不是任何实际项目的默认规则。

## 先完成小型工作底稿

正式写作前，在内部整理“页面/状态 → 对应画面 → 入口 → 行为差异 → 已有说明/来源”。它是防漏写和防配错的工具，不必成为用户文档中的额外表格。

阅读一组有代表性的配对：页面概览、表单、条件展开、确认弹窗、悬浮/禁用及异步反馈。不要只学习一个外观最完整的说明板。若用户只要求单个局部状态，读它及必要的前后状态即可。

画面能说明布局、标签和当前状态；交互原文、原型或用户确认才能支持操作结果、保存策略及业务联动。界面上有搜索框，不能推出实时搜索；字段有星号可以支持必填性，不能推出校验时机。

## 沿用来源粒度，不补写开发规格

先判断一条内容是已有要求、实际矛盾，还是来源没有展开的实现细节。信息没有展开，不意味着必须产生一条待确认事项。

例如 PRD 写：

`Support partner name and email address search (Fuzzy matching)`

文档可以直接沿用。不自行把 Fuzzy matching 改成“不区分大小写、去除首尾空格、关键词包含匹配”，也不为此安排一轮问题。用户另外确认了 Enter / 搜索图标触发时，只补充这个确认过的行为，不继续推导搜索算法。

字符上限、密码编辑策略、重复提交、焦点返回、通知时长和异常恢复等，也先看来源与任务范围。用户要求记录 PRD 原文时，不能为了使清单完整而补写这些规则、建议或“未定义”注释。已有产品要求仍应准确写全；这里限制的是无依据的扩写。

## 文档的两个主体部分

### Entry

交代“从哪里、执行什么、进入哪个状态”。多个入口并列写。默认状态只在与当前行为有关且已有依据时写。

页面入口：`Click Inventory → Platforms in the sidebar.`

抽屉入口：`Click Create Platform on the Platforms page, or Create → Platform in the top bar.`

局部状态入口：`Hover over the ⓘ icon beside the disabled Activate action.`

最后一个是依据当前状态对入口写法的整理，不是参考稿原文。不要给每块悬浮说明重复写模块首页路径。

### Function & Interaction

按页面阅读顺序和用户任务分块。小标题使用真实模块、字段和操作名称，避免独立制造另一套术语。

| 页面类型 | 通常需要覆盖的内容 | 主要验收点 |
| --- | --- | --- |
| 页面/列表概览 | 导航或 Tabs、搜索筛选、列表、行操作、分页 | 数据范围、何时生效、点击去向、可用条件 |
| 新建/编辑表单 | 字段规则、依赖与校验、Confirm/Save、Cancel/关闭 | 输入限制、可提交条件、成功落点、是否保留更改 |
| 局部状态 | 直接触发、变化的内容、退出/恢复 | 与前一状态的差异，无需重述全页 |
| 确认弹窗 | 触发、影响说明、确认、取消 | 作用对象、连带影响、实际提交结果 |
| 异步刷新/上传 | 开始、进行中、成功、失败 | 状态提示、数据变化、后续可操作性 |

这是按需要选用的覆盖清单，不是要求每页都写这些小节。简单悬浮板可只有一个小标题和一两句规则。

## 写清字段契约

按字段实际需要组合：

`字段名 → 必填性/选择方式 → 数据来源与默认值 → 取值限制 → 联动 → 校验与反馈`

示例：`Platform — Required, single choice. Lists all created platforms, including active and inactive platforms, ordered by name from A to Z.`

字段细节不要互相替代：

- “最大 50 字符”不等于达到上限后禁止输入；计数、阻止输入和提交时校验是不同规则。
- “不可用”不等于“隐藏”。依赖上游字段时说明何时可用；切换上游后的清空、保留或重置需要依据。
- “至少填写一组”不等于“只能填写一组”。互斥、至少一项、全部必填应分别表达。
- 日期的可选范围、时分精度、时区和跨日关系分别核对；金额的币种与小数精度分别核对。
- 编辑态说明回填、锁定字段和可修改范围；可引用创建规则，但保存结果和关闭行为仍须可定位。

## 写清动作闭环

对主操作追踪：进入/前提 → 用户动作 → 校验或处理中 → 成功反馈 → 最终位置/数据状态。

对来源明确涉及的 Cancel、×、遮罩点击、Esc、浏览器返回等出口分别核对。相同行为可合并，不同出口不能凭常识认定相同。不因画面有关闭按钮，就要求用户定义全部浏览器导航、键盘和焦点规则。

高影响操作写清影响对象、状态变化、连带影响和恢复方式。停用上级是否影响下级、重新启用时如何恢复，都属于当前项目需要明确的业务规则，不能从通用案例推断。

列表中数字链接需说明目标和携带的筛选条件。来源写“new window”时不要自行改为“new tab”；无法分辨但对实现有影响时集中确认。

## Web 特有的检查，按任务使用

- 搜索：按什么字段、何时触发、清空结果；筛选：单选/多选、即时/确认后生效、组合关系。
- 表格：默认排序、冻结列、横向滚动、溢出展示、分页默认/选项、批量操作选择范围。
- 表单：输入反馈、错误位置与文案、是否保留已填内容、重复提交和异步提交状态。
- 弹层：可否交互背景、焦点进入/返回、键盘顺序、Esc 的退出行为；不擅自给所有弹层统一规则。
- 提示：显示触发、内容、消失触发；非鼠标用户如何获得必要信息。只用颜色表达错误时可作为设计建议指出。
- 导航：同页更新/路由跳转/新窗口、返回后的上下文保留、深链接与权限；按本次范围核对。
- 自适应：目标断点、表格滚动、抽屉或弹窗尺寸、长内容滚动；没有移动端依据时不编造一套移动端稿。
- 数据状态：初次空态、筛选无结果、加载、失败、无权限是不同状态。覆盖与当前任务相关的状态，不把通用清单整段塞入说明。

这些是读取来源时的检查维度，不是必须填满的需求清单，也不是当前项目已证实的通用产品行为。仅在用户请求方案或确有必要时提出建议，并与已确认规则分开。

## 专业语言的取舍

用直接、客观、可验收的句子；复杂规则用条件分支或短列表。使用 `Required`/`Optional`、`single choice`/`multiple choice`、`disabled`/`hidden`、`On success` 等稳定术语。保留 UI 中的精确大小写。

| 含混写法 | 可执行写法（须有项目依据） |
| --- | --- |
| 用户可以操作筛选，方便查找。 | Selecting a filter applies it immediately to the list. |
| 点击后弹出相应页面。 | Click Edit to open the editing drawer with the current values populated. |
| 名称过长正常展示。 | Display up to two lines and truncate overflow with an ellipsis. Hovering over the name shows its full value. |
| 保存成功后正常刷新。 | On success, close the drawer and add the new platform to the top of the list. |
| 不满足条件时置灰。 | Activate is disabled while the parent platform is inactive. |
| 添加失败时提示。 | If the refresh fails, replace the progress message with the specified error message below the field. |

中文同样遵循直接表达：

“单选，必填。按名称 A–Z 排列所有已创建的平台，包含启用与停用状态。”

“点击‘确认’校验必填项及名称唯一性。创建成功后关闭抽屉，新平台显示在列表顶部。”

“上级平台处于停用状态时，‘启用’操作不可用。悬浮提示说明需要先启用上级平台。”

这些句式可复用，其中的业务值必须替换为当前项目规则。精确提示文案不要由语法润色顺带改写。

## 控制长度与未决项

概览只保留帮助理解任务的背景句。不要在每块局部说明重复“这个模块用于管理……”。不把开发接口细节、检查日志或文案冲突的分析过程放进产品说明。

复杂依赖可先用小表或状态流辅助核对，再写入项目允许的形式。没有复杂分支时，用短段落即可。

未决项集中描述“缺少什么、影响哪项用户任务或业务结果”。只有确实阻塞本次交付时才提问，不以“会影响实现”为由扩大问题范围。有明确原文的规则直接写，不因原型不完整逐句加待确认。用户明确要求不补充 PRD 未提及内容时，移除对应问题和建议；用户明确要求保留的待办单独保留。

## 核实差异并收敛结论

- 实际冲突：同一前提下，一张 UX 显示密码字段禁用，另一张却允许输入并报错。先确认前提和状态对应，再询问要采用的业务交互；不能直接根据静态图声称线上逻辑有错。
- 文案差异：PRD 与 UX 仅措辞不同、业务含义相同。简短列出差异，用户选定后使用定稿文案并撤下旧标记，不持续保留“文案待确认”。
- 信息缺省：PRD 没写编辑已有账号时是否需要重新输入密码。这不是已发现的冲突；用户将其交给开发时，不提出默认策略，也不继续注明缺省。
- 用户暂缓：只记录用户明确要求的待办，正文不采用尚未获批的建议。后续一条新消息不自动完成或取消这个待办。

逐项评审时，每次确认一个必要事项。一次确认需要同步检查关联页面、局部说明和汇总板，避免正文已定稿而 `Review Notes` 仍标红。对话历史可放内部工作记录；正式说明保留最终规则和仍可行动的事项。
