# 原型对抗性审查

用于用户明确要求复查原型、核对 PRD、检查流程或总结问题的任务。目标是主动寻找会违反已有规则或阻断用户任务的反例，同时控制误报；不要求固定问题数量，也不因设计来自 AI 就预设存在缺陷。

## 独立建立验收依据

先从本次目标版本的 PRD 和用户定稿提取会影响行为的要求，再与原型比对。不要先读上一轮的自评结论并以此决定检查范围；即使原型和说明相互一致，也可能共同偏离 PRD。

内部底稿可用：

| 要求及来源 | 适用条件 | 预期行为/结果 | 对应画面或路径 | 当前证据与判定 |
| --- | --- | --- | --- | --- |

按当前任务拆分要求，保留 PRD 章节、段落或可定位的原文引用；没有需求编号时使用本次临时编号，不伪称 PRD 原有编号。将复合规则拆到足以独立核对即可，不把未规定的实现细节拆成必答清单。

- 用户明确批准的规则变更优先，记录它覆盖的原要求。当前原型本身、生成者自述和组件默认行为不能自动覆盖 PRD。
- WAP 原型可提供业务入口、字段和流程参考；评审 PC 适配时，根据本次目标和组件约束核对，不能仅因布局或容器不同就认定违反 PRD。
- 只读取本次授权来源与目标范围。PRD 版本不明、原文不可读或关键素材缺失时，明确影响的结论；继续完成已有依据支持的核对，不声称全面符合 PRD。

## 先核要求，再尝试推翻流程

双向检查：每条明确要求能否找到设计表达；每个会改变业务结果的设计行为是否有依据。原型增加的行为若未获确认，标作设计建议或待确认；只有与已有规则冲突或可证实阻断任务时才判缺陷。

从入口走到结果，按本功能实际涉及的分支尝试反例。以下是检查角度，不是必须补齐的产品需求：

- **前提与依赖：** 未满足前提就操作下游；先填下游再切换上游；条件变化后出现隐藏但仍必填、无可选项却必须选择等无法继续的状态。
- **校验与修正：** 按已有规则使用空值、边界值或非法组合；报错后是否存在可完成的修正路径。具体上限、精度、校验时机等仍需来源支持。
- **保存与取消：** 沿已有保存、取消、关闭和返回分支检查状态及数据影响；检查明确表示“未保存”的路径是否却进入已保存结果。
- **结果与恢复：** 主操作是否有相容的结果状态；PRD 明确要求的失败、重试或返回路径是否可达；相同前提是否在不同画面中导向互斥结果。
- **入口与可达性：** 任务入口、关键操作和退出是否对应正确目标；需要点击演示时，检查是否有无法继续的主路径、错误目标或无法关闭的覆盖层。
- **组件限制：** 用户限定只能用现成组件时，检查可读的实例来源、变体和绑定。视觉相似不能证明组件合规；来源不可读时标待验证。修正建议优先用库内已有能力，不建议扩建组件来绕过限制。

局部控件的内部 hover 连线不证明业务路径已连接；普通组件的默认交互不证明业务数据会按 PRD 保存。纯页面评审未要求可点击时，不把缺少连线判为缺陷。

## 根据证据决定结论

| 类别 | 判定条件 | 表达方式 |
| --- | --- | --- |
| 已证实问题 | 明确规则与当前设计相冲突，或当前状态及路径足以证明任务受阻、结果自相矛盾 | 指明依据、位置、路径、预期与现状、影响 |
| 待验证/待确认 | 仅凭静态图无法判断行为、相关状态不可读、版本冲突或缺少必要业务决定 | 说明尚缺什么证据及影响哪项结论，不计入已证实问题 |
| 设计建议 | 有助于改善体验，但没有违反既有要求或可证实的任务阻断 | 与问题分开；未要求建议时可省略 |

PRD 明确要求某个错误提示，但指定评审范围没有对应设计表达时，可以记录“错误状态设计未覆盖”，说明已检查的范围；不能进一步声称线上服务没有校验。截图里没有选中值也不能证明切换后会清空或保留。

若确认“隐藏字段仍被要求填写”，须有隐藏条件及提交约束等证据；只有隐藏态截图而没有校验或规则时，最多提出待验证路径。

优先级按实际影响判断：高为主任务受阻或业务结果错误；中为必要分支或恢复路径受损；低为局部表达或说明不一致且不改变业务结果。证据不足的事项不靠提高优先级冒充已证实缺陷。

## 输出可行动的问题汇总

先概括审查版本、范围、实际验证层级和已证实问题数量及影响，再按影响排序。每条已证实问题包含：

`编号 / 优先级 / 问题 → PRD 或逻辑依据 → 当前画面/节点 → 触发步骤与前提 → 预期 / 观察到的现状 → 用户或业务影响 → 最小修正建议`

表格太宽时改成短条目。需求遗漏写清未被表达的要求及已检查范围；设计矛盾指出两端证据。相同根因影响多个状态时合并一项并列出位置，不重复计算。修正建议不是用户已批准的规则，也不构成修改 UI 的授权。

报告末尾只保留影响结论的待验证/待确认项，以及本次未覆盖的范围。没有已证实问题时写“本次范围内未发现可证实问题”，同时列出验证限制，不声称不存在缺陷或覆盖了全部路径。

实际验证层级区分：需求与静态状态核对、节点/连线检查、可点击演示实走、运行产品验证。只报告完成的层级，不能用画面、连线存在或生成的说明替代实际操作证据。

## 审查后写说明或复查修订

- 同时要求写说明时，先报告问题，再完成确定部分。真实冲突中分别表达 PRD 预期与当前设计，不把原型错误写成正式业务规则，也不以文档声称原型已修好。
- 未要求改 UI 时保留原设计。明确授权修正后，按当前版本更新关联状态与说明，再复查受影响路径。
- 复查时重新读取现有文字、状态和必要截图；只有取得相应证据才关闭问题。规则改变、问题修复和暂时无法验证分别记录，不沿用失效节点或旧结论。
