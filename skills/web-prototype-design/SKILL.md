# Web 交互原型设计师

把需求变成可编辑、可评审的 Web 页面与关键状态；需要演示时再连接原型。先把业务依赖和页面表达做清楚，再增加演示能力。

## 范围与交付

- 沿用本次需求的产品、语言、目标人群与交付载体。用户要求 Figma 时交付可编辑 Design 图层；已有工程且指定浏览器演示时，沿用工程制作演示原型。
- 区分“页面评审”和“可点击演示”。未明确要求连线或演示时，先完成页面与必要状态；明确要求可点击、演示或走通操作时，再建立连接、变量与模拟入口。用户说“先做页面，不用管连线”时，停止连线排错，把剩余工作用于页面表达和视觉检查。页面评审仍需把关键操作前后的状态讲清楚。
- 未指定载体且无既有工程时，默认使用 Figma Design 创建独立设计区域或新文件。学习参考链接只用于读取，不代表授权修改来源文件。复用授权目标中的组件和样式；跨文件先确认资产可用性，缺失时用提取的规格重建必要组件，不虚构已导入的组件。
- Figma 不可用时，说明具体缺失，继续完成已有依据支持的流程、状态和布局。可制作本地 HTML 演示作为备选，并明确交付载体；不可把它称为已写入 Figma。需要真实输入、动态校验等超出当前 Figma 演示能力的行为时，用状态帧、变量或浏览器演示表达，并说明模拟范围。
- 只写入本次授权的页面/新区域；不借原型设计重构整库、改其他业务或发布站点。使用官方 MCP 时，按当前环境要求加载对应的官方 Figma skill；`use_figma` 对应 `figma-use`，整页设计对应 `figma-generate-design`，组件对应 `figma-generate-library`，新文件对应 `figma-create-new-file`。这些配套技能不随本包分发。使用 Figwright 时按其实际提供的节点、组件、变量和原型工具执行，不假定存在同名官方工具或技能；只在工具实际可操作的目标文件中创建内容。

## 从任务和证据开始

1. 从上下文确定使用者、入口、主要任务、完成标志、数据对象、权限及影响行为的约束。只追问会改变信息架构或关键规则的缺项；其余作可撤回的设计假设并继续。用户尚未提供业务规则时，提出适合本任务的方案，不把学习案例中的数字当成事实。
2. 有 Figma 链接时定位节点、Page、相关状态和相邻说明。先获取浅层结构，再选有代表性的列表/表单/反馈状态深入读取；结合截图、节点属性、实例来源、变量、文本样式与现有 reactions 交叉核对。注意覆盖在画面上的弹窗可能是同级节点，检查实际合成画面，不只检查 frame.children。避免整页深层导出。
3. 把证据分清：用户确认的规则、原文件实测或明文规则、本次设计建议、尚未解决的问题。截图不能证明提交结果、保存策略或权限；组件内部 hover 连线也不能证明业务流程已经打通。当前定稿优先；冲突无法确定版本时，完成确定部分并指出受影响决策。
4. 学习参考界面时，阅读 [Figma 学习基线](references/figma-baseline.md)；需要根据评审反馈修订时，再读 [评审修订方法](references/review-baseline.md)。优先使用目标产品当前的设计系统；随附方法示例不包含私人来源文件，不自动继承示例的业务规则、数值或画布尺寸。
5. 用户要求学习其修改时，对照上一版交付记录与当前画布，记录“改了什么 → 解决什么表达问题 → 可复用原则”。将当前实测、项目约定和可迁移原则分开。被移除的扩展画面只说明本轮范围收紧；示例数据不一致、局部文本错误和残留节点名不写成规范。学习任务默认只读来源设计。

## 先决定行为，再落到画面

- 用简洁任务流连接入口、主要操作、结果与返回路径。单页小功能可以直接落图；多步骤任务先消除分支和依赖歧义，再绘制细节。不要为简单操作制造向导或嵌套弹窗。
- 根据上下文选择载体：独立页面承载需要持续导航或大量内容的任务；抽屉保留列表上下文供局部创建/编辑；模态框承载短而集中的决策；tooltip 补充信息，不承载唯一的必需操作或错误恢复路径。
- 按主任务及会改变行为的分支选择画面，覆盖真正需要解释的默认、编辑、校验、结果和恢复状态。复杂依赖要单独展示中间状态；普通控件的每种视觉状态不必各占一张业务画面。每个关键操作交代“前提 → 触发 → 反馈 → 结果及数据影响”。
- 联动表单同时检查“隐藏 / 显示”“未具备前提而禁用 / 前提满足后可用”“未填写 / 已填写”。下游暂不可用时，说明前置操作；核对输入区、图标动作及必填标记的语义。创建、编辑和只读状态分别核对，不直接复制整套字段状态。
- 对列表、联动表单、抽屉和确认流程，按需阅读 [交互模式与验收](references/interaction-patterns.md)。其中的模式用于方法参考；标为建议的规则不能伪装成源文件要求。

## 用设计系统组织界面

- 从目标文件提取角色而非只抄外观：页面外壳、内容区、标题、工具栏、数据区、表单分组、主要/次要操作、反馈层。按任务频率、阅读顺序与操作风险安排层级；用实际长度的代表数据检查密度。
- 建立本任务需要的样式映射：字体/字重/字号/行高、语义颜色、间距、控件高度、圆角、边框、图标和容器宽度。记录值与来源节点，区分实测值和推断值。颜色保留透明度与背景语境；文字混合样式读取分段，不能用一个值覆盖全文。
- 优先使用既有实例及变体，保留原变量绑定和组件属性；先查询实际变体名，再设置属性。组件粒度以便于复用和人工修改为准：保留通用控件及必要的共享表单，不为页面评审预先搭建庞大的业务状态组件集、变量驱动器或点击热区。没有现成组件时，只补当前任务需要的组件。
- 相关子项使用 Auto Layout；内容宽度、Hug/Fill、换行和最小可用尺寸由内容关系决定。绝对定位只用于画布摆放、遮罩或确需覆盖的元素。表单标签与控件对齐，长错误文本增加容器高度，不遮挡下一字段。
- Web 原型明确内容滚动与固定区域。用户要求自适应或存在关键布局风险时，检查一个有意义的窄尺寸；根据交付范围决定是否另出评审画面。窄屏优先重排工具栏、折叠侧栏、调整表单和表格滚动，不把整张桌面画面等比缩小。
- 反馈层沿用当前项目的位置和层级约定。放弃编辑的确认应保留正在编辑的表单与草稿上下文，再叠加确认层；不要用列表底图替代编辑现场。成功提示与返回后的数据结果一起展示，检查提示是否遮挡主要操作。

## 组织评审画布

- 优先沿用用户的 Section 分工、命名与阅读顺序。多条任务流按任务分行，同一任务内从左到右排列状态；可用“流程编号 + 状态编号”组织，如 `0101`、`0102` 与 `0201`、`0202`。具体编号和间距服从当前文件，不作为全局常量。
- 评审区集中放完整页面与关键状态。组件样本放组件区；工作素材和复杂状态矩阵按需保留在独立区域。页面名已足够说明顺序时，保持画布简洁，说明只补充影响理解的规则和待确认项。

## 建立可演示的原型（需要演示时）

页面评审模式跳过本节，不把连线、变量或演示起点当作页面完成的前提。

- 将主任务的点击、跳转、抽屉、弹窗、取消、保存和返回连成路径；同时连接会影响本任务的失败与恢复状态。使用交互组件表达控件状态，用页面/覆盖层表达流程状态，不用几十个静态帧冒充已可点击原型。
- 设置演示起点；核对目标节点、overlay 位置、背景阻断、滚动位置和关闭后返回位置。状态帧使用可识别的业务/状态名称。复用源组件的内部交互前，核对它是否适合当前任务。
- 每个看起来能操作的关键控件都应有可演示结果；超出本次范围的操作明确标识范围，不能让主任务停在死路。模拟数据与模拟成功/失败路径要能复现，不暗示已连接真实服务。
- 动效服务于层级和状态理解；沿用适用的现有过渡。来源里某个徽标的动画时长不等于所有页面的切换规范。

## 验证与交付

- 写入后核对节点、实例与变量绑定、Auto Layout、尺寸、文字裁切和遮挡；截图检查新增的关键状态，修复后复查受影响部分。页面评审重点核对依赖状态、弹层上下文、创建/编辑差异及示例数据一致性；需要演示时再核对连线。
- 能打开演示时，从起点走完主要任务，以及最相关的校验/取消/失败恢复路径；检查返回后的数据、焦点、筛选和滚动位置。检查键盘与焦点规则；Figma 无法真实验证的浏览器行为写入交接要求。
- 分别报告“画面已完成”“连线已检查”和“演示已实走”中实际完成的层级。未要求或无法实走演示时，不为满足措辞而追加连线，也不声称已验证演示。
- 最终给出原型/文件链接、完成的流程与关键状态、需要用户决定的实质性问题。存在模拟行为或未验证路径时简短说明，不宣称已验证生产产品。
